MemoryLink 백엔드 설계

앱이 실제로 연결된 서버는 Firebase 하나이고, 앱이 부르는 서버 코드는 없습니다. 그래서 Firestore 보안 규칙이 사실상 백엔드의 전부입니다. 10/3 점검 때는 고친 규칙이 운영에 없었고, 10/4에 v2 규칙과 보호자 웹을 배포했습니다. 9월에 만든 AWS EC2는 앱과 연결되지 않았고, 쓰지 않기로 했습니다. 무료 요금제에는 TTL 자동 삭제가 없어서, 보관 기간이 지난 데이터는 GitHub Actions 예약 작업이 매일 지웁니다.

10/4 구현 상태 지금 구조 문제 12가지 목표 구조 보호자 링크 v2 연결 순서 결정할 것 근거

추천. Firebase(서울 리전)를 유일한 영구 백엔드로 정하고, 건강 데이터의 원본은 계속 휴대폰 SQLite에 둡니다. 클라우드에는 보호자에게 보여줄 최소 사본과 문의만 올립니다.

서버 코드는 기기가 혼자 못 하는 일에만 씁니다. 조용해진 어르신 감지, 보호자 푸시, AI 키 보관, 주인 없는 문서 청소가 그것입니다. EC2는 사라질 서버로 보고 출시 기능을 올리지 않습니다.

이 설계는 새 계획이 아닙니다. 9/28 출시 감사의 P0-05~P0-08·P0-10과 2단계 계획 S2-01·S2-04·S2-05를 실제 실행 순서로 묶은 것입니다.

3. 목표 구조: 가장 좋은 연결

휴대폰의 원본은 그대로 두고, 클라우드는 Firebase 하나로 모읍니다. 화면이 꺼져 있어도 보호자 사본이 살아 있게 하고, 서버 판단이 필요한 일만 2단계에서 Cloud Functions로 올립니다.

설계 원칙

  • 원본은 휴대폰에 둡니다.계정·건강 기록·일기·훈련 원자료는 SQLite에 남깁니다. 클라우드에는 보호자에게 보여줄 사본과 문의만 둡니다. 오프라인에서도 앱이 돌고, 유출 범위와 신고할 데이터가 작아집니다.
  • 영구 백엔드는 Firebase 하나입니다.인증·규칙·호스팅이 이미 있고 Firestore가 서울 리전입니다. Supabase나 AWS로 옮기면 인증, 데이터 계층, 보호자 웹을 다시 만들어야 합니다. 지금 문제는 플랫폼이 아니라 누가 무엇을 언제까지 읽고 쓰는가라는 계약입니다.
  • 규칙이 1차 서버입니다.무료 요금제에서도 규칙으로 필드 허용목록, 값 범위, 소유자 불변, 만료를 강제할 수 있습니다. 1단계까지는 서버 코드 없이 갑니다.
  • 서버 코드는 기기가 혼자 못 하는 일에만 씁니다.조용해진 어르신 감지와 보호자 푸시, AI 키 보관, 주인 없는 문서 청소입니다. 이것들은 Blaze 요금제의 Cloud Functions(서울)에 둡니다.
  • 모든 서버 호출은 같은 신분증을 씁니다.앱은 이미 있는 firebase_auth로 ID 토큰을 받아 Authorization: Bearer로 붙입니다. 서버는 구글 공개키와 프로젝트 ID만으로 검증하므로, EC2 같은 외부 서버에도 서비스 계정 키를 둘 필요가 없습니다. 앱 의존성 추가도 없습니다.
  • EC2는 사라질 서버로 취급합니다.출시 기능, 특히 보호자 안전 기능을 올리지 않습니다. 쓰더라도 저장 없는 계산만 맡깁니다.

4. 보호자 링크 v2

가장 중요한 연결이라 따로 정합니다. 한 링크를 비공개 문서와 공개 사본 두 개로 나누고, 만료를 '마지막 성공 + N일'로 밉니다. 어르신이 앱을 계속 쓰는 동안은 QR을 다시 찍을 필요가 없고, 쓰지 않게 되면 링크가 저절로 닫힙니다.

필드guardian_links · 비공개guardian_views · 공개 사본이유
ownerUid있음없음공개 응답에서 소유자 식별자를 뺍니다
expiresAt있음같은 값규칙이 두 값의 일치를 강제합니다
createdAt, schema있음schema만다음 이행에 대비합니다
display_name—있음아이디 대신 사용자가 정한 호칭
today_steps, weekly_steps, weekly_avg—있음정수·범위를 규칙으로 검사합니다
scores—최대 4개, 0~100카테고리 이름은 글자로만 표시합니다
is_anomaly, anomaly_message—있음경고 카드
contact—이상 상태 + 동의 시에만누구의 번호인지부터 결정이 필요합니다

규칙 초안

공개 사본을 쓸 때 비공개 문서의 소유자를 getAfter()로 확인합니다. 두 문서를 한 번의 batch로 쓰므로 새 링크도 같은 검사를 통과합니다.

function link(t)      { return get(/databases/$(database)/documents/guardian_links/$(t)).data; }
function linkAfter(t) { return getAfter(/databases/$(database)/documents/guardian_links/$(t)).data; }
function validExpiry(e) {   // N = 30일 제안 + 기기 시계 오차 1일
  return e is timestamp && e > request.time && e <= request.time + duration.value(31, 'd');
}
function viewFields() {
  return ['schema', 'display_name', 'today_steps', 'weekly_steps', 'weekly_dates', 'weekly_avg',
          'scores', 'is_anomaly', 'anomaly_message', 'contact', 'last_sync', 'last_heartbeat', 'expiresAt'];
}

match /guardian_links/{token} {   // 비공개: 소유자와 만료일만
  allow get, delete: if isSignedIn() && resource.data.ownerUid == request.auth.uid;
  allow create: if isSignedIn()
    && request.resource.data.ownerUid == request.auth.uid
    && request.resource.data.keys().hasOnly(['ownerUid', 'createdAt', 'expiresAt', 'schema'])
    && validExpiry(request.resource.data.expiresAt);
  allow update: if isSignedIn()   // 만료일 연장만 허용
    && resource.data.ownerUid == request.auth.uid
    && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['expiresAt'])
    && validExpiry(request.resource.data.expiresAt);
}

match /guardian_views/{token} {   // 보호자가 읽는 공개 사본
  allow get: if resource.data.expiresAt > request.time;
  allow create, update: if isSignedIn()
    && linkAfter(token).ownerUid == request.auth.uid
    && request.resource.data.expiresAt == linkAfter(token).expiresAt
    && request.resource.data.keys().hasOnly(viewFields())
    && request.resource.data.today_steps is int
    && request.resource.data.today_steps >= 0 && request.resource.data.today_steps <= 100000;
  allow delete: if isSignedIn() && link(token).ownerUid == request.auth.uid;
}

초안입니다. 실제 규칙에는 나머지 필드의 타입·길이 검사와 서버 시각 검사를 모두 넣고, 에뮬레이터 테스트로 허용·거부를 고정한 뒤에만 배포합니다. v2 규칙은 만료 필드가 없는 옛 문서를 읽지 못하게 하므로 기존 링크는 배포와 함께 끊깁니다. 공개 출시 전이라 테스트 데이터일 가능성이 크지만, 끊어도 되는지 확인이 필요합니다.

하트비트

공유 중일 때만 백그라운드 서비스가 1시간마다 오늘 걸음 수와 시각을 공개 사본에 씁니다. 보호자 웹은 마지막 하트비트가 오래되면 '정상'이라고 쓰지 않고 '3시간째 소식 없음'처럼 보여줍니다. 서버 계산이 없어 무료 요금제에서 됩니다. 공유 사용자 1명당 하루 쓰기 24건이라 무료 한도(하루 2만 건)로 약 800명까지 버팁니다. 백그라운드 isolate에서 Firebase를 초기화해 쓰는 부분은 실기기 검증이 필요한 기술 위험이라, 1단계의 첫 작업으로 확인합니다.

5. 연결 순서

0단계 · 지금 바로

무료 요금제 · 앱 의존성 추가 없음 · 약 1주(추정)

순서가 중요합니다. 빨간 번호는 승인이 필요한 운영 작업입니다.

  1. 운영 규칙을 내려받아 보관합니다.콘솔의 규칙 기록이 롤백 기준입니다. 운영 응답으로 확인하면, 없는 보호자 문서를 읽을 때 404가 나와 아직 예전 규칙입니다(v2라면 403).
  2. 규칙 테스트를 만듭니다.앱 pubspec과 분리된 Node 테스트 폴더를 두고, 에뮬레이터에서 컬렉션별 허용·거부 표를 돌립니다. 이 PC에 Firebase CLI 15.19와 JDK 21이 이미 있습니다.
  3. 앱에 재발급 경로를 넣습니다.쓰기가 거부되면 128비트 새 토큰을 만들어 QR을 바꿉니다. 보호자 웹은 403·404를 '만료되었거나 잘못된 링크'로 안내합니다. 규칙보다 먼저 나가야 하는 이유는 문제 5입니다.
  4. 규칙과 보호자 웹을 배포합니다.재발급 경로가 든 앱이 테스트 기기에 깔린 뒤 규칙, 그다음 보호자 웹 순서입니다.
  5. 운영 데이터를 정리합니다.global_stats 문서와, 정상 상태인 옛 보호자 문서의 전화번호 필드를 지웁니다.
  6. API 키 정리(바뀜).보호자 웹은 키 없이도 같은 응답을 받는 것을 운영에서 확인해, 페이지에서 키를 뺐습니다. 그래서 키를 나눌 필요가 없고, 안드로이드 키의 앱 제한만 유지하면 됩니다.
  7. 작은 정리를 한 묶음으로 합니다.난이도를 SQLite로 옮기고 클라우드 동기화를 끊습니다. 문의 규칙에 작성자 불변·크기 제한·작성자 삭제를 넣습니다. 관리자 쓰기는 당분간 콘솔(규칙을 거치지 않음)로 하고 앱의 관리 쓰기 버튼은 숨깁니다. 릴리스 빌드는 AI를 끄고, wttr.in·HuggingFace 경로와 목업 서버, Supabase SQL을 걷어냅니다.

7. 근거

직접 확인한 것 · 10/3

  • Firestore (default)는 네이티브 모드, 위치 asia-northeast3입니다. Firebase CLI로 확인했습니다.
  • 운영 guardian.html은 HEAD판과 같고 작업 트리판과 다릅니다. 배포본을 내려받아 대조했습니다.
  • firestore.rules의 마지막 커밋은 7/14이고, 이후는 미커밋 수정뿐입니다.
  • 보호자 웹과 안드로이드 앱이 같은 API 키를 씁니다. 값은 출력하지 않고 일치만 비교했습니다.
  • EC2는 Tailscale에 온라인이고, 확인한 포트 중 22번만 응답합니다. 80·443·8000·8080·3001은 닫혀 있습니다.
  • 계정의 Supabase 프로젝트 3개는 모두 INACTIVE입니다.
  • 앱 코드에 EC2·Supabase·CloudFront 주소가 없습니다.
  • 이 PC의 Firebase CLI 15.19.0이 memorylink-7af26에 접근할 수 있고, JDK 21이 있습니다.

확인하지 못한 것

  • 운영 Firestore 규칙의 실제 내용. 콘솔에서 확인해야 합니다.
  • 요금제, 예산 알림, API 키 제한, App Check 상태.
  • 운영 문서 수와 전화번호가 남은 문서 수. 운영 데이터는 읽지 않았습니다.
  • EC2에 설치된 것, 보안 그룹이 인터넷에 여는 포트, 프로그램 종료 뒤 처리.
  • Supabase 프로젝트 중 어느 것이 MemoryLink용인지.

외부 문서

  • Gemini API 추가 약관: 무료 등급 입력은 제품 개선과 사람 검토에 쓰일 수 있고, 민감 정보를 넣지 말라고 적혀 있습니다. 유료 등급은 개선에 쓰지 않습니다.
  • Firestore 요금: TTL 삭제는 무료 사용량이 없고 결제가 필요합니다. 무료 한도는 하루 읽기 5만, 쓰기 2만, 삭제 2만 건입니다.
  • Firestore TTL: 만료 뒤 보통 24시간 안에 지우며, 지워지기 전까지는 조회됩니다.
  • Firebase AI Logic과 App Check: 2026-11-02부터 강제되고 해제할 수 없습니다.
  • Firebase AI Logic 요금: Spark는 Gemini Developer API 무료 등급만, Vertex AI 경로는 Blaze가 필요합니다.
  • App Check 강제 모드: 강제하면 유효한 App Check 토큰이 없는 요청을 거부합니다.
  • ID 토큰 검증: 자체 서버는 공개키와 프로젝트 ID만으로 검증할 수 있습니다.
  • 익명 인증: Identity Platform의 자동 정리를 켜면 30일 지난 익명 계정이 지워집니다. 익명 uid를 소유자로 쓰는 동안은 켜지 않습니다.
  • Tailscale Funnel: 포트를 열지 않고 공개 HTTPS 주소와 인증서를 붙입니다.
